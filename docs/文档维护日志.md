# 文档维护日志

> **用途**：记录每次文档维护对应的代码 tag 与一句话总结。
> 服务于三种场景：**继续维护 / Agent 中断重启 / 日后回溯**。

---

## 为什么需要（价值论证）

**这个做法有价值，而且价值被低估了。** 理由有三：

### 1. 它解决一个真实的"对不上"问题

文档版本（v1.18）与代码版本（tag m6a）是**两套独立编号**。
没有日志时，你只知道"文档是 v1.18"，但不知道**它对应哪次提交**——
而这才是最关键的信息：**这份文档描述的是哪个状态的代码？**

### 2. ★ 它是 Agent 中断重启的唯一可靠锚点

新会话的 Agent **不知道自己上一版写了什么、改到哪了**。
它能读到文档，但读不到"这份文档是基于哪个提交写的"。

有日志后，开场白只需一句：
> "先读 `docs/文档维护日志.md` 最后一行，确认当前基线是 `m6a`，再读 v1.18 文档。"

这比让 Agent 猜强得多——**它甚至能自己判断文档是否落后于代码**。

### 3. 它让"先提交再刷新文档"这条纪律可执行

没有日志时，"先提交还是先刷新"只是个口头约定，违反了也没痕迹。
有日志后，每一行都必须写 tag 号——**写不出来就说明顺序错了**。

## 格式（每行一条，倒序追加，新的在上）

```
| 文档版本 | 对应 tag / commit | 日期 | 一句话总结 |
|---|---|---|---|
| v1.20 | `star-tracking` / cdcab79 | 2026-10-17 | 增速榜改按日均排序（可比性修正）；项目收尾：SSOT 改固定文件名、docs 清理过程性文档 |
| v1.19 | 待定（本轮仅文档，无代码改动） | 2026-10-17 | REA 诊断结案；star 追踪立项；**SSOT 改固定文件名**；docs/ 整理规范落地 |
| v1.18 | `m6a` / 4a12fa3 | 2026-10-17 | 新增 star 追踪需求与文档维护规范；M6b 暂缓 |
```

**字段说明**：

| 字段 | 要求 |
|---|---|
| 文档版本 | 两份 SSOT 的 N（必须一致） |
| 对应 tag / commit | **先提交代码再刷新文档**，才能写得出这一栏 |
| 日期 | 维护当天 |
| 一句话总结 | 只写**变更要点**，不写过程 |

## ★ 命名约定（v1.19 起）

**SSOT 文件名固定，不带版本号**：`AI_Pulse_设计方案.md` / `AI_Pulse_Agent开发执行手册.md`。

- 版本标识：**文档第一行**写明当前版本
- 历史追溯：**本文件**（文档版本 ↔ tag/commit）+ git
- 更早曾用带版本号的文件名（`_v1.7` … `_v1.19`），**已于 v1.19 废弃并删除**

## 固化成的规范（写进执行手册）

1. **每次文档维护必须在本文件顶部追加一行**，不得遗漏
2. **必须先提交代码并打 tag，再刷新文档**——否则 tag 栏写不出来
3. **两份 SSOT 版本号必须一致**，不一致视为维护未完成
4. **Agent 不得修改本文件**（与 SSOT 同样的只读约定）
5. 新会话开场白固定包含一句："先读 `docs/文档维护日志.md` 最后一行确认基线"
