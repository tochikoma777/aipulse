# 预言生成降级 · 根因分析与修复指令

> 现象：M6a 收尾的真实运行中，**`predict_generate` 仍然 degraded，生成 0 条预言**
> （`prediction_generation.llm_calls=1`，日志 `llm.structured.degraded`）。
> 而同一天的 `brief` 却是 `degraded=false`、四字段全部非空。

**优先级：高于 M6b。** 预言生成 0 条 = **记分板不再增长**，这是本项目核心资产受损。

---

## 一、关键线索：brief 成功、predict 失败，差别在哪

| | brief | predict |
|---|---|---|
| prompt | `daily_brief.j2` v3 | `generate.j2` |
| **模型档位** | **`fast`（deepseek-chat）** | **`strong`（deepseek-reasoner）** |
| 结构化输出 | `json_schema` → 自动降级 `json_object` → **成功** | `json_schema` → `json_object` → `plain` → **仍失败** |

**DeepSeek 的实际情况**：`deepseek-chat` 支持 `json_object`；
**`deepseek-reasoner` 两个 structured 参数都不支持**，只能靠第三级 `plain`（文本解析）。

所以 brief 走的是"降级一次就成功"的路径，而 predict **必须靠 plain 兜底**——
**plain 只要出问题，就是 0 条**。

---

## 二、为什么 M4 收尾时能生成 5 条，现在 0 条

| | M4 收尾时 | M6a 后 |
|---|---|---|
| 分析窗口 | 约 7 小时 | **24 小时** |
| items | 1 | **174** |
| **候选证据池** | **1 条** | **Top 30-50 条（含标题+摘要）** |
| 结果 | generated 5 | **degraded，0** |

**窗口修复是好事**（这正是我们想要的），但它让 predict 的输入上下文**膨胀了约 10 倍**。

对 `reasoner` 的连锁影响：
1. 输入长 → 思考时间更长
2. 输出 5 条带判据的预言本身就长，**reasoner 还要先输出思维链**
3. → 撞 `max_tokens` 上限 → 输出被截断成不完整文本 → plain 解析失败 → degraded

**这正好是我此前预警过、但当时"实测无截断迹象"所以没动的那一项。**
现在数据规模变了，它暴露了。

---

## 三、★ 修复步骤（按顺序，不要跳）

### 第 0 步：先拿到诊断证据（不要盲改）

**在 degraded 分支打印原始输出的前 500 字符 + 字符长度**，写入 `llm_usage.error` 或日志。

这一步能**立刻区分**两种完全不同的失败：

| 表现 | 结论 | 修法 |
|---|---|---|
| 输出被切断（`...判据：截至到期日，若...` 戛然而止） | **截断** | 调 max_tokens |
| 输出完整但不是 JSON（带解释文字） | **格式问题** | 改 plain 的解析或 prompt 约束 |

**没有这一步，后面全是猜。**

### 第 1 步：`max_tokens` 按 fast / strong 分档

配置项 `llm.max_tokens_fast` / `llm.max_tokens_strong`（或 `timeout` 同款透传机制），
**strong 至少为 fast 的 2-3 倍**（reasoner 有思维链输出）。

> ⚠️ **注意此前的教训**：`timeout_s` 就是因为"配置写了但不透传"而变成死配置的。
> **改完必须验证代码真的读了这个值。**

### 第 2 步：★ 收窄候选证据池（这条可能比 max_tokens 更关键）

当前池取 Top 30-50 且**每条带摘要**——窗口变 24h 后这是巨大的上下文负担。

**改为：Top 20，每条只给 `id + 标题`，不给摘要。**

理由：
1. **省输入 token**（直接降低成本）
2. **减少干扰**：长上下文中模型更容易跑偏、更容易引用池外 id
3. **标题足以让模型判断相关性**——它要的是"引用哪条"，不是"读懂每条"
4. 真需要正文时，验证阶段会重新检索完整证据（那时是单条，不担心长度）

**这一条同时改善成本、稳定性、幻觉率，性价比最高。**

### 第 3 步：若仍失败 —— 重新权衡 predict 是否该用 strong

这是一个需要认真对待的权衡：

| 方案 | 优势 | 劣势 |
|---|---|---|
| `strong`（reasoner） | 推理质量可能更好 | **两个 structured 参数都不支持**，只能靠脆弱的文本解析；更贵；更慢 |
| `fast`（chat） | **支持 json_object，结构化可靠**；更便宜更快 | 推理深度可能不如 reasoner |

**我的倾向**：先按第 0-2 步修。如果 reasoner + plain **结构性不可靠**（反复失败），
**就改用 `fast`**。

理由是**本项目"宁缺毋滥"的原则反过来也成立**：
> **"生成 0 条"比"质量稍差但有 5 条"糟糕得多。**
> 记分板的价值建立在样本量上，一条都生成不出来，质量上限再高也没意义。

**但先修后改**：第 0-2 步很可能就解决了，不要一上来就降档位。

---

## 四、验收标准

| 要看到的 | 说明 |
|---|---|
| `prediction_generation.generated >= 3` | 不再 0 条 |
| `llm.structured.degraded: false` | 未降级 |
| 若仍走 plain 降级 | **可接受**，但要说明是 plain 救回的（说明第三级兜底有效） |
| 证据 id 抽查 | 随机抽 1 条，确认 id 在对照表里能查到 |

## 五、附：把这条写进踩坑实录

这是一个很有教育意义的案例，建议在 `docs/踩坑实录.md` 补一条：

> **修复一个 bug 可能引爆另一个看似无关的 bug。**
> 我们把分析窗口从 7 小时修成 24 小时（正确修复），
> 结果预言生成从 5 条变成 0 条——因为**输入上下文膨胀 10 倍**，
> 撞上了此前"实测没暴露"的 max_tokens 限制。
>
> 教训：**"实测没暴露"不等于"不存在"，只说明当时的数据规模还没触发它。**
> 修改数据规模相关的参数后，要回头检查所有依赖上下文长度的环节。
