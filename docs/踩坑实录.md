# 踩坑实录

> 本文档记录 aipulse 开发中真实踩过、且**有普适教育意义**的坑。
> 它们不是流水账，而是每一条都可能在你自己的项目里复现。

**一个总纲**：本项目 20+ 个 bug 中，最危险的那一类**全部只有真实运行才暴露**。
本地桩测试全绿 ≠ 真实可用——这句话我们用了 7 个 bug 才学到。

---

## 一、配置类

### 1. pydantic-settings 中，YAML 字面量会压过环境变量

**现象**：`AIPULSE_MODE=hybrid` 在 CI 里明明设了，实际一直按 `full` 跑，且**不报错**。

**根因**：`Settings(**load_yaml(path))` 把 YAML 值作为 **init kwargs** 传入，
而 pydantic-settings 中 **init kwargs 优先级高于环境变量**。
同一份 YAML 里，`api_key` 写的是 `${ENV}` 占位符（手工插值，能生效），
`mode` 写的是硬编码字面量（**静默失效**）——两套机制并存是灾难。

**解法**：划线区分
- **环境开关** → `${ENV}` 占位符（可被覆盖）
- **算法阈值** → 字面量（要 git 版本化、可复现实验）

**教训**：**混用两套配置机制会静默失效**，而且不报错、不崩溃，最难发现。

---

### 2. 配置写了但不透传，等于没写

**现象**：`llm.timeout_s: 120`，实际超时是 20 秒。

**根因**：建 HttpClient 时没传超时参数，于是吃了默认值 20s。
配置字段存在、有文档、有默认值——**但没有任何一行代码读它**。

**解法**：超时按 fast/strong 分档透传（strong 180s，因为推理模型有思维链输出，耗时是 chat 的数倍）。

**教训**：**配置项有没有被真正读取，必须验证**。写了不等于生效。

---

## 二、数据源类

### 3. ★ 状态型源 vs 事件型源：一个持续热门的项目"只出现一天"

**现象**：某个 GitHub 项目连续三天在 Trending 榜上，日报里只在第一天出现，之后永久消失。

**根因**：两类源的时间语义根本不同，被混为一谈。

| 类型 | 源 | 时间语义 |
|---|---|---|
| **事件型** | arXiv / HN / RSS | `published_at` = 事件发生时刻，固定不变 |
| **状态型** | **GitHub Trending** | **没有发布时间**，只有"此刻是否在榜" |

Trending 是**当前快照**。采集时给它赋了首次采集时刻，之后跨天重复采集时
通过 `content_hash` upsert 合并——**合并保留首次发现时间**。于是它滑出第二天的窗口。

**解法**：Item 增加 `last_seen_at`（每次 upsert 都更新），按 `time_semantics: event|state`
选择过滤字段——**状态型用 `last_seen_at`**。

**附带收益**：可以计算「连续在榜 N 天」，比单日热度更能说明真火。

**教训**：**给没有时间戳的数据强行赋予时间戳，是隐蔽且严重的建模错误。**

---

### 4. 索引滞后：严格 24h 窗口永远采空

**现象**：arXiv 按 24 小时窗口采集，永远返回 0 条。

**根因**：arXiv Atom 的 `published` 是提交日，索引滞后 3-4 天
（当天 10-13 查，最新条目是 10-09）。

**解法**：放宽到 `lookback_days: 7` 并在放宽时告警。

**教训**：**第三方数据的时间语义要实测，不能假设**。

---

### 5. 快照间隔太短 → 速率虚高到荒谬

**现象**：两次采集间隔 2 分钟，算出 star 增速 **1247.97 /小时 ≈ 日增 29951**。

**根因**：机制正确、数值不可用。短窗口放大瞬时波动。

**解法**：`min_velocity_window_hours: 6.0`，间隔不足标 `insufficient`，
**但绝对增量仍如实记录**（不丢数据，只是不给速率）。

**教训**：**"机制成立" ≠ "数值可用"**。宁可不给数字，也不要给离谱数字——
一个荒谬的数值对可信度的伤害，比没有更大。

---

## 三、LLM 集成类

### 6. ★ 静默降级：功能一直没生效，但系统看起来正常

**现象**：配了 API key 以来，**AI 点评从未真正生效过**，日报每天照常产出，没人发现。

**链路**：`json_schema` 不支持 → 降级 `json_object` → 也不支持 → `degraded`
→ 点评为空 → **但日报照样生成，退出码 0**。

**三重根因**：
1. **档位选错**：主编点评是轻任务却走了 `reasoner`（推理模型不支持结构化输出参数）
2. **降级阶梯缺一级**：只有 `json_schema → json_object`，缺了万能兜底
3. **降级状态记成全局布尔**：支持情况其实**按模型而异**，全局记忆会连坐

**解法**：
- 轻任务走 `fast`（`deepseek-chat`）——**这才是根本修法**，改完直接好，且更便宜更快
- 补第三级 `plain`：不带 `response_format`，prompt 内嵌 schema，从文本解析
- 降级状态按 `(model, format)` 记忆

**教训**：**"降级了"不等于"功能可用"。**
降级必须可见——我们后来把 `llm.degraded` 提到了简报显眼位置。

---

### 7. 模型会编造引用 id

**现象**：分析窗口里只有 1 条 item，模型却产出 4 条预言、共 8 个证据 id。

**解法**：两层防护，**只做事后校验不够**（会导致证据不足时全部拒收，什么都拿不到）
1. **预防**：把候选证据池（id + 标题）注入 prompt，要求"只能逐字复制该列表里的 id"
2. **校验**：id 必须存在于池内，否则重写 → 仍不合法则丢弃

**更重要的认识**：**这个问题的真正根因是分析窗口太窄**（见坑 3/6 的窗口问题）。
窗口只有 1 条时，无论如何也凑不出 4 条预言 × 2 条证据。**先修数据供给，再修校验。**

**教训**：**LLM 的引用必须可核验**。事后我们让 `predictions.md` 输出证据对照表，
查不到标 ⚠️——把一次性人工核验变成**每天可查的常态化能力**。

---

### 8. 缓存键设计：两种响应格式会串

**现象**：自动降级前后，同一 prompt 命中了错误的缓存结果。

**根因**：`json_schema` 与 `json_object` 两种响应格式共用同一个缓存键。

**解法**：缓存键追加 `:js` / `:jo` 后缀。

**教训**：**缓存键必须包含所有会影响结果的维度**。这个 bug 极难排查，因为缓存命中看起来是"优化生效"。

---

## 四、CI / 部署类

### 9. Actions 无状态环境：目录不存在导致建库失败

**现象**：全新 clone 运行报 `unable to open database file`。

**根因**：`data/` 目录只被 `.gitignore` 覆盖，仓库里没有占位文件；
`engine_for()` 早有 `mkdir`，但 **alembic 那条路径漏了**。

**教训**：**本地复用旧数据会完全掩盖这类问题**——只有删掉 `data/` 才等效于 CI 环境。

---

### 10. 报告 commit 冲突 → 当天数据丢失

**现象**：`git push` 被拒 → 当天报告丢失（**报告即数据库，不可恢复**）。

| 尝试 | 结果 |
|---|---|
| 直接 `git push` | 被拒即丢 |
| `git pull --rebase` | **同日重跑必然内容冲突** → 还是丢 |
| **`git fetch` + `git reset --soft FETCH_HEAD`** ✅ | 把本次报告作为新提交叠在远端最新之上 |

---

### 11. 本地测不到 ≠ 源不可用

**现象**：本地 WSL 中 Reddit / HF / Import AI 三个源 DNS 被污染，完全不可达。

**错误做法**：按"本地测不到 = 源不可用"写采集器 → 永久丢失三个高质量源。

**解法**：`availability: always | actions_only` 分级。
本地跳过、不计失败、不影响退出码；CI 环境全开（实测 13/13 全通）。

**教训**：**开发机网络 ≠ 生产环境网络**。用分级而非删除来应对。

## 五、工程细节类

| 坑 | 说明 |
|---|---|
| `expire_on_commit` 是 **Session 参数**，不是 engine 参数 | 否则 session 关闭后报 `DetachedInstanceError` |
| SQLModel 字段名 `date` 与 `datetime.date` 冲突 | `from datetime import date as date_type` |
| 凭印象写 `# type: ignore[...]` 错误码 | mypy 会报"未使用的 ignore"，用 `cast()` 或查准错误码 |
| 正则 `<p[^>]*>` 误匹配 SVG 的 `<path>` | 必须写 `<p(?:\s[^>]*)?>` |
| Typer `invoke_without_command=True` 回调带子命令时也触发 | 加 `ctx.invoked_subcommand is not None` 判断 |
| `--json` 输出被日志污染，脚本无法解析 | `--json` 时日志走 stderr，stdout 保持纯 JSON |
| 坏 gzip 响应写进 HTTP 缓存会持续复现 | 排查时用 `--no-cache` |
| 后台 `serve` 不 `nohup` 会被回收 | curl 表现成 `status=000`，不是页面 bug |
| Jinja 中 `foo.bar` 先取属性再取键 | dict 用下标，否则取出 `dict.items` 方法本身 |

## 六、M6c 知识库类

### 12. ★ item_id 在日报和页面里根本不显示

**现象**：`aipulse knowledge note it_xxx` 可用，但用户从 `brief.md`、`index.html`、`_results.html`
都找不到 `item_id`；`aipulse search` 还是占位。

**根因**：`item_id` 只在 `daily.json` 的 `items` 键和内部模板变量里存在，从未渲染。
用户能看见的稳定定位键只有 **URL**，标题是展示文本。

**解法**：新增 `knowledge items` 列出条目，`note` / `mark` 支持 `--url` 与 `--query`；
`--query` 多条候选只列出、不自动选择，避免静默选错。

**教训**：**内部主键 ≠ 用户可用的定位键。** 设计笔记/收藏类入口前，先问"用户从哪拿到这个 id"。

---

### 13. ★ 本地主库过期，不能拿它校验 item_id

**现象**：本地 `data/aipulse.db` 停在旧 `alembic_version`，没有 M6b 的 `item_enhance` 表；
但 `daily.json` 已经有 23 条 why。若用主库校验最新 item，写笔记会直接失败。

**根因**：M6c 的数据源是 **committed `data/reports/**/daily.json` + 本地笔记**，
不是本地主库；本地主库只是采集缓存，可能落后于报告。

**解法**：位置 `item_id` 只查 daily index；索引外条目必须显式 `--allow-unknown`。

**教训**：**先确认"数据在哪里"再写校验逻辑**；不要拿一个可能过期的库当唯一真相。

---

### 14. `.gitignore` 的 `data/*.db` 只匹配顶层

**现象**：`data/knowledge/notes.db` 这种嵌套数据库不会被忽略，可能被 commit；
仓库是 public 时，个人笔记直接公开。

**根因**：gitignore 的 `*` 不跨 `/`，`data/*.db` 只覆盖 `data/` 直接子文件。

**解法**：用户库固定在 `data/user_data.db`（`data/` 顶层）；`data/knowledge/` 整目录忽略；
测试/文档都明确这条路径约束。

**教训**：**密钥/私人数据放在哪里，不能靠"看起来被忽略了"来判断**；用 `git check-ignore -v` 逐路径验证。

---

### 15. ★ 本地 daily 会制造未跟踪报告，和导出不能共用一个工作区

**现象**：本地跑一次 `aipulse daily` 会写 `data/reports/<date>/` 下 8 个文件；
随后 `git status` 非空，导出 cron 的"工作区不干净"检查直接跳过。

**根因**：daily 的渲染落盘是无条件的；`--no-collect` / `--skip-llm` 只跳过采集或 LLM，
不会跳过报告。`data/reports` 又不被 `.gitignore` 忽略。

**解法**：方案 E——**导出 cron 不跑本地 daily**，只 `pull --ff-only` + `knowledge export`；
本地 daily 只作为手动/备份入口，不安装到同一个 cron 流程。

**教训**：**"写文件的流水线"和"要求工作区干净的流程"必须分居**，否则会永久互相阻断。

---

### 16. `git status --porcelain` 会让自动化永久跳过

**现象**：`data/inbox/` 等未跟踪文件长期存在；只要用 `git status --porcelain` 判空，
导出 cron 每次都认为"工作区不干净"，永远不执行。

**根因**：`--porcelain` 包含未跟踪文件；而 pull 真正需要关心的是**已跟踪/已暂存改动**。

**解法**：`if ! git diff --quiet || ! git diff --cached --quiet; then ... fi`。
注意：远端要创建同名未跟踪文件时，`pull --ff-only` 仍会失败，这是另一个边界。

**教训**：**判断"能不能 pull"和判断"工作区有没有未跟踪文件"不是一回事**；
自动化里每个检查都要写清语义，否则会静默关闭自己。

---

### 17. 导出失败只 `>>log 2>&1` 会静默退出

**现象**：`set -euo pipefail` 下，`$AIPULSE_BIN knowledge export >>log 2>&1` 失败时
脚本直接退出，日志没有 "FAILED" 行，也无法区分"成功"与"成功但无新数据"。

**解法**：用 `if cmd; then ... else code=$?; ... fi`，成功记录 `export OK total=N`，
失败记录 `export FAILED exit=code` 并退出。

**教训**：**重定向不等于处理错误**；`set -e` 只保证退出，不保证留下可诊断的日志。

---

### 18. 501 条分片测试最初 O(n²) 超时

**现象**：每加一条都重新渲染整个候选 chunk，501 条测试直接把 pytest 拖死。

**解法**：逐条渲染一次 + 增量计算 header/body 字节，复杂度降到线性；
同时用 200KB 分片测试覆盖体积阈值。

**教训**：**分片逻辑要在构造 500+ 条数据下测**；只测 2-3 条永远发现不了性能与边界问题。

---

## 七、一句话总结

> **最危险的 bug 都不报错。**
> 静默降级、静默失效的配置、静默滑出窗口的数据、静默命中的错误缓存——
> 它们让系统"看起来正常"，直到某天你发现 AI 点评其实一直是空的、
> 或者某个热门项目其实已经消失了三天。
>
> 应对方法只有一个：**把关键状态显式暴露出来并每天检查**
> （我们的做法是：`llm.degraded` 进简报、证据 id 出对照表、
> `signals` 三态可观测、Actions 报告每天 commit 可 diff）。

### 8.1 修复一个 bug 可能引爆另一个看似无关的 bug

**现象**：把分析窗口从 7 小时修成 24 小时（正确修复），
结果预言生成从 5 条变成 **0 条**。

**根因链**：窗口 24h → items 1 → 174 → 候选证据池从 1 条涨到 30 条（带摘要）
→ 输入膨胀约 10 倍 → reasoner 先输出思维链、再输出 5 条长预言 → 撞 `max_tokens=4000`
→ 内容截断（实测 first_len=3442）→ plain 解析失败 → degraded → 0 条。

**解法**：
1. `max_tokens` 按 fast/strong 分档（strong 8000），并验证真的透传到 `chat()`
2. 候选池收窄到 Top 20，只给 `id + 标题`，不注入摘要
3. 修复后在 Actions 实测 `generated=5, inserted=5`

**教训**：**"实测没暴露"不等于"不存在"，只说明当时的数据规模还没触发它。**
修改数据规模相关的参数后，要回头检查所有依赖上下文长度的环节。

---

### 8.2 ★ 证伪条件：点值区间和合取都会制造"判定悬空"

**现象**：trend 的 watchlist 对 `it_77f9ddd43bbeeb71` 写了两条分支——
「仍在榜且热度 ≥82.89 → 证伪」「跌出或热度 <82.06 → 维持」。
实际 10-22 热度 82.82：不 ≥82.89，也不 <82.06 → **两个分支都不触发，判定悬空**。
代码侧其实已经是穷尽二分（`selfcheck.py:463` 只按 `still_on`/`dropped` 判），
悬空的恰恰是 LLM 写在文本里的那两个点值阈值。

**两种坏写法**

1. **点值阈值**：任何 `≥ / ≤ / 超过 / 以上 / 不低于 82.89` 都会在两个阈值之间留出灰色地带。
2. **合取**（更隐蔽）：「是否出现新进榜条目，**同时** X 与 Y 是否仍在榜」——
   两个独立观测有 4 种组合状态，而分支只有 2 个，必然覆盖不全。
   我第一版校验器只查了阈值，所以 S4 首跑没抓到这条，是**离线复算**才发现的。

**解法**
- 结构上只允许**单一二元可观测状态**（如「10-23 是否仍在 Top30」），两分支天然互斥穷尽。
- prompt 里明写正反例（预防），校验器同时查阈值与"≥2 个是否"（检测）——
  **只补检测不补预防，重跑必然复现**。
- "是否同时公开 A、B、C 三项"是单一问句，不能误伤（已加单测）。

**判据也要配套**：不合格的条件**只标记不可用**，不判整场失败；
只有可用数为 0 才真的没有可判定结论。用"整场失败"换"过度声称"是同一种错误的另一面。

**教训**：**"两个分支"不等于"互斥且穷尽"**——写完条件后必须自问：
任意实际值是否都必然落入某一分支？

---

### 8.3 证据包的板块分布决定了输出的分歧空间

**现象**：debate 首跑的证据包 15 条里 14 条是「论文与研究」，
结果四个 persona 全部收敛到"论文 vs 非论文"这一根轴上——
表面上有 4 条关键分歧，其实是同一场争论换了个说法。

**根因**：取材只按「议题相关度 + 热度」排序，而议题关键词（Agent）恰好密集命中论文板块。

**解法**：按板块轮转取材，每板块 Top 3-4（15 条 → 4 个板块 4/4/4/3）。
改完立刻出现真正不同轴的分歧：结论方向、证据缺席能否否证、评测协议归属、时间尺度。

**教训**：**输入分布决定输出的分歧空间**。当多个模型的结论高度一致时，
先怀疑是不是输入偏斜把它们锁进了同一个框架，而不是急着庆祝"达成共识"。

---

### 8.4 ★ "双层分离"会撞上自检的输入契约

**现象**：把 weekly.md 改成给人看的三句话 + 表格后，L1 立刻失败——它要求
7 个 `## N. 上升主题…` 小节、每节至少 1 个裸 `item_id`、全文 2000-4000 字，
新模板一条都不满足。

**根因**：L1-L4 一直把**人类文档**当机器输入。一旦人类层开始"减负"，
校验就跟着崩——而"不许为排版删数据"的红线又不能破。

**解法**：机器层单独落 `weekly.json`（7 节正文 + 裸 ID + violations + caveats），
L1-L4 改读它，四层判定逻辑一行未改。

**教训**：**先定"校验读哪一层"，再动人类层**。顺序反了就要返工。

### 8.5 ★ 产物分目录会静默丢掉跨期历史

**现象**：`watchlist.json` / `calibration.json` 跟着周报拆进 `<窗口末日>/` 后，
L3/L4 每期只看到自己那一条记录。

**根因**：`_load_state()` 原本读 `trend/watchlist.json` 这一个文件，
分目录后它只读本期目录。

**解法**：`_load_state(state_dir, name)` 合并 `state_dir/name` 与 `state_dir.parent/*/name`，
`entries` 按 `(issue, item_id)` 去重、`issues` 按 key 去重。

**教训**：**这个 bug 不报错**——回检"看起来正常"，只是永远没有历史。
凡是"改路径"的改造，都要检查所有"按路径读状态"的地方。

### 8.6 ★ 结构化字段输出了，但在映射处被漏掉

**现象**：debate 人类层要"每方 3 条核心论据"，prompt 里写清了，模型也输出了，
但渲染出来的文档里一条都没有。

**根因**：`_round1` 里把 `stance` / `reasoning` / `falsification` / `cited_item_ids`
都拷进了 report，唯独漏了 `key_points` 这一行。结构化输出多一个字段，
映射处不补一行，它就静默消失——`summary` 里也看不见（没进摘要），只能靠肉眼发现。

**解法**：补 `stmt.key_points = parsed.key_points[:3]`，并在 `summary()` 里加
`key_points` 计数，让"漏拷"至少能被指标暴露。代价是重跑一次真实调用（¥0.17）。

**教训**：**schema 加字段 ≠ 数据被用上**。加字段时同步三处：prompt、映射、指标。

### 8.7 ★ 检验对象选错：拿"条目存活"去验"结构判断"

**现象**：L4 首跑报 fail——上一期周报在「结构变化/二阶影响」里声称的三条，
隔一天全部跌出 Top30，存活率 0%。

**为什么这个 fail 不成立**

1. **间隔只有 1 天**。榜单日换血 70%+、66% 条目只出现 1 天，1 天内跌出是**常态基线**，
   不是过度声称的证据。拿它判 fail，等于用噪声定罪。
2. **样本 0/3**，没有统计意义。
3. **更根本：量错了对象**。结构判断说的是板块/来源结构（"社区舆论在收缩"），
   而检验用的是条目的在榜状态。板块份额上升不代表代表条目必须在榜；
   三条全跌出也证伪不了"社区舆论在收缩"。

**解法**

- 主判据换成**上一期的结构方向在本期是否延续**：
  记录 `heat_migration.direction` 与 `source_share.count_delta_pp` 的符号，
  下一期同 scope 同 name 的方向是否相同 → 延续率。
- 前置门：间隔 <7 天 或 可判样本 <5 → `insufficient`（**不是 fail**）。
- 条目存活率降为辅助指标，只记录不判死。
- 加反馈闭环：结论写 `admission.json`，下一期 `trend` 据此收紧结构判断的准入。

**教训**：**"没通过"不等于"实现错了"，也不等于"判据对了"。**
先问一句：这个判据检验的，和判断声称的，是不是同一层的东西？
（同时记住反面：也不能为了让判据通过就调低阈值——那是另一个方向的错。）

### 8.8 ★ 别断言 rich 输出里的长选项名（同一个坑第三次）

**现象**：`assert "--range" in result.output` 在本地绿、CI 红。
CI 上 rich 按 80 列折行，`--range` 被截成 `--ran…`。

**这是同一个坑的第三次**：`--topic`（M5 S4）、`--range`（本轮）——都是"断言 CLI 帮助文本
里的长选项名"。本地终端宽，CI 固定 80 列，于是只有 CI 能复现。

**解法**：这类断言一律改成**只断言退出码与语义文本**（如 `BadParameter` 的退出码 2、
`off 档` 这种不会折断的短词）。需要"必须给 --topic"这类行为，用退出码覆盖，不要用选项名。

**教训**：**凡是断言 `--xxx` 的用例，等于给 CI 埋一颗定时炸弹**。写之前问一句：
这个词会不会被 rich 折断？
